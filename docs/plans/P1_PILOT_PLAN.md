# P1 试标与可行性验证计划

## 目标

用最小成本验证三件事：标签是否可判、授权偏差是否能稳定提取、选择性治理是否优于“全部审批/静态阈值”。本阶段不追求论文最终指标。

## 输入与规模

- 先构建 100～150 个场景组，每组 2～5 个候选调用变体。
- 覆盖文件、Shell、Git、HTTP/API、密钥、CI/部署六类工具族。
- L0～L4 均需出现；L3/L4 至少占试标集的 25%，避免高危样本过少。
- 只纳入合成或已脱敏的结构化样本，不执行样本携带的命令。

## 执行步骤

1. 冻结 `case.schema.json` 的 P1 版本并验证全部输入。
2. 三名标注者独立标注首批 50 条，计算加权 Kappa 与动作一致率。
3. 对分歧建立裁决表，回写标注手册，不直接修改模型适配分歧。
4. 扩展至 300～500 条，按 `scenario_group` 切分。
5. 建立三条基线：硬规则、成本敏感逻辑回归、梯度提升树。
6. 比较宏 F1、L3/L4 漏判率、覆盖率-风险曲线、审批率和 ECE。
7. 形成 P1 评审：继续、调整标签体系，或缩小研究问题。

## 退出条件

- Schema 通过率 100%，无跨集合场景组泄漏。
- 加权 Kappa 目标值 0.70；若低于 0.60，先修订定义，不进入大规模标注。
- 端到端脚本能从清洁环境生成相同切分与指标文件。
- 至少一种学习基线在给定 L3/L4 漏判预算下，审批率低于“全部审批”。

## 交付物

`pilot-0.1` 数据清单、裁决记录、切分清单、基线报告、失败案例表和下一阶段 Go/No-Go 决策。
